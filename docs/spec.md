## 1. カレンダー層（実装済み）

### 1-1. 予定の識別

- **単発予定**: `eventIdentifier` のみをキーにする。
- **繰り返し予定**: `eventIdentifier` + `occurrenceDate`（その回の元の開始時刻）。

繰り返しかどうかは EventKit 側（`hasRecurrenceRules || isDetached`）で判定する。
開始時刻をキーに含めないため、時刻を動かしても同一の予定として認識される。

### 1-2. 枠（1日あたりのサポート対象）

- 無料版は1日3件、Premium は無制限。
- **第1段階（前日まで）**: 開始時刻の昇順で上位3件。同一時刻は `eventIdentifier` の昇順。
- **第2段階（確定後）**: 空き枠がある場合のみ、`creationDate` の昇順（登録順）で追加する。
  既に確定した枠は押し出さない。
- 対象外: 終日予定、座標が恒久的に解決できなかった予定、対象日に重ならない予定。
- 日跨ぎ予定は、またぐ全ての日でそれぞれ1枠を消費する。
- **開始済みの予定は枠の候補にしない。** 対象日が今日で無料版のとき、開始時刻が
  現在時刻より前の予定は第1段階・第2段階のどちらでも対象外。前日にアプリを開かなかった
  場合の救済であり、初回起動か2回目以降かで扱いが変わらない。
  ただし既に枠を持っている予定は例外で、開始済みでも枠を手放さない。
  対象日が翌日の場合はこの条件を適用しない（前日の夜に始まる日跨ぎ予定を落とさないため）。

### 1-3. 枠の解放

| 状況 | 枠 |
| --- | --- |
| 完了した（予定はカレンダーに残っている） | 保持する |
| 支援を送信する前に予定が消えた | 返す（次の予定に回る） |
| 支援を送信した後に予定が消えた | 返さない（消費済みとして数える） |

場所が無かった予定に後から場所が追加された場合は、第2段階の通常の追加として扱う。
空き枠があれば入り、無ければ入らない。1日の上限3件は常に超えない。

### 1-4. 完了判定

`now >= event.startDate` で完了とする。終了時刻ではなく開始時刻が基準。
通知の送信有無は完了の条件にしない。終日予定は開始時刻が 0:00 なので、その日になれば完了扱い。

完了後はスナップショットを凍結する。外部で編集されても値を更新せず、編集回数も増やさない。
外部で削除されてもスナップショットは保持する。UI 側での編集・削除のブロックは後続フェーズで扱う。

### 1-5. 変更検知

比較対象は `startDate` / `endDate` / `latitude` / `longitude` の4項目のみ。
タイトルやメモは保存も比較もしない。同時に複数項目が変わっても編集は1回と数える。
無料版は `editCount >= 3` で上限とするが、上限を超えても計算は最新のデータで続行する。

### 1-6. 座標の解決

開始時刻順に1件ずつ逐次で解決し、枠が埋まった時点で打ち切る（通常ちょうど3回）。
第2段階では登録順で解決する。並行実行はしない（レート制限のため）。

| 結果 | キャッシュ | 枠 |
| --- | --- | --- |
| 成功 | 保存（無期限） | 消費する |
| 一時的な失敗（通信断・レート制限） | 保存しない | 消費する |
| 恒久的な失敗（住所として解決できない） | 保存（24時間） | 消費しない |

### 1-7. アプリ起動時の戻り値（LaunchResult）

`CalendarLayer.refreshOnLaunch(now:)` が返す。

| フィールド | 内容 | 範囲 |
| --- | --- | --- |
| `todayEvents` | 今日に重なる予定（終日含む、開始時刻順） | 今日 |
| `tomorrowEvents` | 翌日に重なる予定（終日含む、開始時刻順） | 翌日 |
| `todaySlots` | 今日の枠 | 今日 |
| `tomorrowSlots` | 翌日の枠 | 翌日 |
| `conflicts` | 予定どうしの重複 | 今日 |
| `editLimitExceededKeys` | 無料版で `editCount >= 3` に達した予定 | **今日のみ** |
| `outOfSlotKeys` | 枠に入らなかった予定 | **今日のみ** |
| `noLocationKeys` | 座標が解決できなかった予定 | **今日のみ** |
| `allDayKeys` | 終日予定 | **今日のみ** |
| `carriedOverKeys` | 前日以前から続く日跨ぎ予定 | **今日のみ** |

`tomorrowEvents` があるのは、Premium が開始1.5時間前から通知するため、翌日 0:00〜1:30 に
始まる予定は今日のうちに出発時刻を計算する必要があるから。`tomorrowSlots` は `EventKey` の
配列しか持たず、開始時刻も座標も取れない。

キー配列を今日ぶんのみに保つのは、翌日ぶんを混ぜると `carriedOverKeys` の「対象日ごとに
意味が変わる」性質を表現できなくなるため。翌日ぶんの日跨ぎ判定は `tomorrowEvents` と
`tomorrowSlots.date` から導出する。

```swift
let carriedOver = result.tomorrowEvents.filter {
    !calendar.isDate($0.startDate, inSameDayAs: result.tomorrowSlots.date)
}
```

`noLocationKeys ∩ todaySlots.confirmedKeys` が「枠は持っているが出発時刻を計算できない
予定」にあたる（2-3 の「前のサポート対象に場所がない場合」の判定）。

### 1-8. 保存期間

| データ | 削除条件 |
| --- | --- |
| スナップショット | 完了から14日経過 |
| 枠の状態 | その日が3日より前 |
| ジオコーディング（成功） | 削除しない |
| ジオコーディング（失敗） | 24時間経過 |

14日なのは、週次サマリーが「先週」を表示するため。月曜に閲覧する場合に最大13日前が必要になる。

## 2. 移動時間（実装済み）

`DeparturePlanner` が計算する。移動時間そのものは `TravelTimeService` 越しに受け取るだけで、
`CatCore` は MapKit を知らない。実装は `CatPlatform.MapKitTravelTimeService`。

### 2-1. 移動手段の判定

| 条件 | 移動手段 |
| --- | --- |
| 直線距離 1.5km 以下 | 徒歩 |
| 直線距離 1.5km 超 | ユーザーが選択した交通手段（電車 / 車） |

ユーザーの選択は `UserPreferences.primaryTransport`（`.transit` / `.automobile`）に持つ。

直線距離は大円距離（Haversine）で求める。CoreLocation の `CLLocation.distance(from:)` は
WGS84 の測地線距離なので、同じ2点でもわずかに違う値になる（1.5km 付近で数メートル程度）。
判定を Linux 上でテストできるようにするため、CatCore 側で計算している。

### 2-2. 出発時刻

```
出発時刻 = 開始時刻 − 移動時間 − 10分
```

バッファの10分は全ての交通手段で一律。徒歩でも電車でも車でも変えない。

### 2-3. 出発地点

| 対象 | 出発地点 |
| --- | --- |
| その日の最初のサポート対象 | 自宅 |
| 2件目以降 | 前のサポート対象の場所 |
| 前のサポート対象に場所がない | 自宅 |

自宅の座標は `UserPreferences.homeLatitude` / `homeLongitude` に持つ。

「その日の最初」は開始時刻の昇順で判定する。連鎖は日ごとに独立していて、翌日も自宅から始まる。

座標が解決できなかった予定（`noLocationKeys` に含まれるもの）は出発時刻を算出せず、
連鎖では「場所がない」として扱う。日跨ぎ予定は枠を消費するが、出発時刻の計算は開始日にのみ行う。

### 2-4. 移動時間を取得できなかった場合

出発時刻は算出せず、`DeparturePlan.Outcome.travelTimeUnavailable` に落とす。

- **枠は解放しない。** オフライン時に枠を失うより保持するほうが損失が小さい。
  一時的な失敗は次回起動時に自然に再試行される。専用の再試行機構は設けない。
- **移動時間が取得できなかったことを伝える通知を送る**（実装は通知フェーズ）。
- 失敗しても予定の場所自体はあるので、**次のサポート対象の起点にはその場所を使う**。
  2-3 の「前のサポート対象に場所がない場合」には当たらない。

### 2-5. 交通機関の所要時間を引く基準時刻

`MKDirections.Request` の `arrivalDate` に**予定の開始時刻**を指定する。バッファの10分は
そのあと別に引く。知りたいのは「その時刻に着くには何分かかるか」であり、現在時刻基準だと
翌朝の予定を深夜のダイヤで計算してしまう。

交通手段では出し分けず、徒歩・車・電車のすべてで指定する。Apple のドキュメントは
`arrivalDate` を「サーバーが経路を最適化するための追加情報」としか説明しておらず、
交通機関に限る記述も徒歩で無視されるという記述も無いため。

## 3. オンボーディング（未実装）

初回起動時に次を必須で設定させる。

| 項目 | 保存先 | 必須 |
| --- | --- | --- |
| 自宅の座標 | `UserPreferences.homeLatitude` / `homeLongitude` | **必須** |
| 主な交通手段（電車 / 車） | `UserPreferences.primaryTransport` | 必須 |

**自宅の座標が未設定の状態は想定しない。** その日の最初のサポート対象は自宅を起点に
するため（2-3）、未設定だと出発時刻を算出できない。オンボーディングを完了したかどうかは
`UserPreferences.hasCompletedOnboarding` に持つ。

計算層は防御的に `DeparturePlan.Outcome.originUnavailable` を返せるようにしてあるが、
通常フローでは発生しない。

## 4. 通知（後続フェーズ・未実装）

以下は確定した仕様。**このリポジトリのコードには一切反映していない。**

### 4-1. 通知タイミング

| プラン | 通知 |
| --- | --- |
| Free | 出発時刻 / 開始時刻 の2回 |
| Premium | 開始1.5時間前 / 開始1時間前 / 開始30分前 / 出発時刻 の4回 |

### 4-2. 移動時間を取得できなかった場合

移動時間が取得できなかったことを伝える通知を送る。枠は解放しないので、その予定は
サポート対象のまま残る（2-4 を参照）。

### 4-3. 出発時刻が変わった場合

| 条件 | 挙動 |
| --- | --- |
| Premium で出発時刻が10分以上早まった | 即時通知 |
| 新しい出発時刻が既に過ぎている | 緊急通知 |

### 4-4. カレンダー層との接続

通知を送信したら `EventSnapshot.supportSentAt` に送信日時を記録する。
呼び口は `Repository.markSupportSent(for:at:)`。この値が枠を返すかどうかの判定に効く
（1-3 を参照）。
