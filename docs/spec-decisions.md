# 仕様決定の記録

カレンダー層の実装中に仕様の矛盾・不足として上がった論点と、その決定内容。
「なぜそう決めたか」を残すのが目的で、決定そのものは確定済み。

---

## 決定1: EventKey から開始時刻を外す

### 決定

```swift
public struct EventKey: Codable, Equatable, Hashable {
    public let eventIdentifier: String
    /// 繰り返し予定の回を区別するための、その回の元の開始時刻。単発予定は nil。
    public let occurrenceDate: Date?
}
```

- **単発予定**: `eventIdentifier` のみ。`occurrenceDate` は nil。
- **繰り返し予定**: `eventIdentifier` + `occurrenceDate`（その回の元の開始時刻）。

繰り返しかどうかの判定は EventKit 側で行う。`EventKitCalendarSource` が
`event.hasRecurrenceRules || event.isDetached` で判定し、真のときだけ
`occurrenceDate` を入れる。`isDetached` も見るのは、系列から切り離された回
（単独で編集された回）が `hasRecurrenceRules == false` になることがあるため。

### 理由

当初の仕様は `EventKey = eventIdentifier + startDate` だったが、これは
「開始時刻の変更 = editCount 1」と両立しない。開始時刻がキーの一部だと、時刻を
動かした瞬間にキーが変わり、**編集ではなく「削除＋新規」**として見えてしまう。
編集回数の上限が「予定を動かしすぎたら諦める」ためのものである以上、これは抜け穴になる。

`occurrenceDate` は予定を動かしても変わらないので、

- 繰り返し予定の各回を区別する（当初の目的）
- 時刻を動かしても同一の予定と認識する（編集回数の目的）

の両方を同時に満たせる。単発予定には回の概念が無いので `occurrenceDate` は不要で、
むしろ入れると時刻変更でキーが変わってしまう。

### 影響

- `EventSnapshot.startDate` は引き続き可変フィールドとして「今の開始時刻」を持つ。
  キーの時刻（識別用）とスナップショットの時刻（変更検知用）は別物。
- 日跨ぎ判定や範囲判定にはキーの時刻を使わない。予定の現在の `startDate` を使う。
- キーの並び順は `eventIdentifier` 昇順 → `occurrenceDate` 昇順。開始時刻順に
  並べたい場合は `CalendarEvent.isOrderedBefore` を使う。
- **この変更以前に保存されたデータとは互換性が無い。** 旧形式は `startDate` を
  必須キーとして持っており、新形式では単発予定として読まれてしまう。未リリースの
  ため移行処理は入れていない。既存の `snapshots.json` / `slots.json` は破棄する。

## 決定2: CalendarEvent に creationDate を追加

### 決定

```swift
public let creationDate: Date?   // EKCalendarItem.creationDate
```

第2段階の追加順（`registrationOrdered`）は `creationDate` の昇順で決める。
`creationDate` を持たない予定は最後に回し、その中では開始時刻順で並べる。

### 理由

第2段階は「登録順で追加」と決まっているのに、`CalendarEvent` に作成日時が無く、
`fetchEvents` は開始時刻順で返す仕様だったため、**登録順が事実上機能していなかった**。
`EKCalendarItem.creationDate` がそのまま登録順になるので、モデルに持たせた。

### 影響: LocationResolver の処理順にも波及した

`LocationResolver` は候補を順に処理して枠が埋まった時点で打ち切るため、
**解決の順序がそのまま「どの予定が枠の候補になれるか」を決めてしまう**。
候補を常に開始時刻順に並べていると、空き枠が1つのとき「開始時刻がいちばん早い
未確定の予定」だけが候補になり、登録順は結果に影響しない。

そこで `resolveLocations` に処理順を選ぶ引数を足した。

```swift
public enum CandidateOrder {
    case startTime   // 第1段階（開始時刻順に上位 N 件）
    case asGiven     // 第2段階（登録順で追加）
}
```

`CalendarLayer` は第2段階の残り候補を `creationDate` 順に並べてから `.asGiven` で
渡す。ジオコーディングの呼び出し回数は枠数を超えないまま、登録順が実際に効くようになる。

## 決定3: 枠の解放は「支援を送信したか」で決める

### 決定

予定がカレンダーから消えたとき、その枠を返すかどうかは支援の送信状況で決める。

| 状況 | 枠 |
| --- | --- |
| 支援を送信する前に消えた | **返す**（次の予定に回る） |
| 支援を送信した後に消えた | **返さない**（消費済みとして数える） |

「一度埋まった枠は繰り上がらない」という当初の記述は、
**「支援を送信済みの枠は繰り上がらない」** に読み替える。

### 理由

1日の上限は「何件サポートしたか」の上限であって、「何件枠に入れたか」の上限ではない。
支援を送る前に消えた予定は、ユーザーから見れば何も起きていないので、枠を占有し続ける
理由が無い。逆に送信済みの通知は取り消せないので、その枠は消費されたものとして数える
必要がある。ここを返してしまうと、朝に3件・昼に3件…と1日に何件でもサポートされてしまう。

### 実装

- `EventSnapshot.supportSentAt: Date?` を追加。支援を送信した日時を記録する。
  値を入れるのは後続フェーズの通知処理で、`Repository.markSupportSent(for:at:)` を用意した。
- `DailySlots.releasedSlotCount` は `supportSentSlotCount` に改名し、意味も変えた。
  「支援を送信済みのまま予定が消えたため、返せなくなった枠の数」を数える。
  送信前に消えた予定はここに数えない。
- 第2段階で追加できる件数は
  `slotLimit - （残っている確定枠の数） - supportSentSlotCount`。

`supportSentSlotCount` を `DailySlots` に持たせているのは、判定を起動をまたいで
保つため。消えた予定のスナップショットは削除されるので、次回起動時には
「支援を送っていたかどうか」を確かめる術が無くなる。数だけ持ち越せば足りる。

### 完了した予定との違い

完了した予定は枠を持ち続ける。これは解放の話ではなく、**予定がカレンダーに残っている**
から。完了しても取得結果に含まれ続けるので、そもそも解放の判定にかからない。

## 決定4: 場所を後から追加された予定の枠

### 決定

「新たな枠を消費しない」は **「1日の上限3件を超えない」** という意味。
場所が無かった予定に後から場所が追加された場合は、第2段階の通常の追加として扱う。

| 状況 | 結果 |
| --- | --- |
| 空き枠がある | 枠に入る |
| 枠が埋まっている | 枠に入らない |

一度枠を逃した予定が以後も枠を取れない、という制約は設けない。

### 理由

守りたいのは「1日に3件までしかサポートしない」という上限であって、
「どの予定が枠を取れるか」の固定ではない。場所を後から埋めるのはユーザーの
ごく自然な操作で、それを理由にその日ずっと候補から外す理由が無い。
上限は第2段階の空き枠計算がそのまま担保する。

### 実装

追加の実装は不要だった。第2段階の追加可能件数
（`slotLimit - 残っている確定枠 - supportSentSlotCount`）が上限を保証している。
座標が解決できた時点で `slotEligible` に入るので、空き枠があれば自然に追加される。

`CalendarLayerTests` に3件のテストを足して挙動を固定した。

- `testEventGainingALocationTakesAFreeSlot`
- `testEventGainingALocationIsRejectedWhenSlotsAreFull`
- `testLateAddedLocationsNeverPushTheDayAboveThreeSlots`

## 決定5: 完了判定は開始時刻だけで決める

### 決定

`now >= event.startDate` で完了とする。**通知の送信有無は完了の条件にしない。**

### 理由

「開始時刻 → 通知後すぐ完了」は「開始時刻を過ぎたら完了」という意味であり、
通知の送信を待つという意味ではない。通知を条件にすると、通知が失敗した予定が
永遠に完了しなくなる。また、完了判定を通知フェーズに依存させると、カレンダー層だけを
Linux 上でテストできなくなる。

判定が開始時刻の比較だけで済むので、バックグラウンド実行も要らない。
アプリ起動時に全予定を評価するだけで足りる。

### 補足

終日予定は開始時刻が 0:00 になるため、その日になった瞬間に完了扱いになる。これは仕様どおり。

## 決定6: 完了後の「編集・削除不可」はカレンダー層の責務ではない

### 決定

カレンダー層の責務は次の2つまで。

- 完了後はスナップショットを凍結する（値を更新せず、編集回数も増やさない）
- 外部で削除されてもスナップショットを保持する

UI 側での編集・削除のブロックは後続フェーズで扱う。

### 理由

カレンダー層は EventKit から読むだけで、ユーザーが純正カレンダーアプリで行う編集や削除を
防ぐ手立てを持たない。防げないものを責務にすると実装できない仕様になる。
できるのは「外部で何が起きても、こちらの記録を壊さない」という防御側の担保だけで、
それは凍結と保持で足りている。

## 決定7: LaunchResult に翌日の予定本体を追加する

### 決定

`LaunchResult` に `tomorrowEvents: [CalendarEvent]`（翌日に重なる予定、終日含む、
開始時刻順）を追加する。

キー配列（`editLimitExceededKeys` / `outOfSlotKeys` / `noLocationKeys` /
`allDayKeys` / `carriedOverKeys`）は **今日ぶんのみ** という現在の仕様を維持する。

### 理由

Premium は開始1.5時間前から通知するため、翌日 0:00〜1:30 に始まる予定は今日のうちに
出発時刻を計算する必要がある。ところが `tomorrowSlots` は `EventKey` の配列しか持たず、
**翌日の予定の開始時刻も座標も取得できなかった**。通知フェーズが着手できない欠落だった。

キー配列を今日ぶんのみに保つのは、翌日ぶんを混ぜると `carriedOverKeys` の
「対象日ごとに意味が変わる」性質を表現できなくなるため。同じ日跨ぎ予定が、開始日には
含まれず翌日には含まれる、という区別が失われる。

### 翌日ぶんの日跨ぎ判定

`tomorrowEvents` と `tomorrowSlots.date`（翌日の0時）と、呼び出し側が注入した
`Calendar` があれば判定できる。**追加の情報は要らない。**

```swift
let carriedOver = result.tomorrowEvents.filter {
    !calendar.isDate($0.startDate, inSameDayAs: result.tomorrowSlots.date)
}
```

`CalendarLayerTests.testCarriedOverCanBeDerivedFromTomorrowEvents` でこの導出を固定してある。

## 決定8: 第2段階にも開始済み予定の除外を入れる

### 決定

第1段階と同じ除外条件を第2段階にも適用する。対象日が今日で、無料版のとき、
**開始時刻が現在時刻より前の予定は枠の候補にしない。**

ただし **既に枠を持っている予定は例外**。開始済みでも枠を手放さない
（完了済みの予定が枠を保持し続けるルールと同じ）。

### 理由

第1段階の除外は「完了済みの予定が枠を食い潰し、その日サポートが効かなくなる」ことへの
救済だが、同じ問題は第2段階でも起きる。仕様の書き漏れと判断した。

副次的に、開始済みの予定に対して過去の出発時刻が算出され、
「新しい出発時刻が既に過ぎている → 緊急通知」が誤って発火することも防げる。

### 揃った挙動

変更前は、同じ予定がその日の初回起動か2回目以降かで報告のされ方が変わっていた。

| 14:00 に起動 | 9:00 の予定（変更前） | 変更後 |
| --- | --- | --- |
| その日の初回（第1段階） | どこにも報告されない | どこにも報告されない |
| 2回目以降（第2段階） | `outOfSlotKeys` に現れる | どこにも報告されない |

### 実装

- `CalendarLayer`: 除外条件から「第1段階のみ」の判定を外し、既に枠を持つ予定を
  例外にする形へ統一した。ジオコーディングの呼び出し枠も無駄にしない。
- `SlotConfirmer.secondStage`: 追加候補のループで開始済みの予定を飛ばす。
  枠の保持側（`accounting.keptKeys`）にはこのフィルタをかけないので、
  開始済みでも既存の枠は失われない。
- 対象日が翌日の場合はこの条件が効かない。日跨ぎ予定（前日の夜に始まる）を
  落としてしまうため。

## 決定9: noLocationKeys の定義は現状維持

### 決定

「実際にジオコーディングまで到達したのに座標が無いもの」を確定とする。
一時失敗（`.temporaryFailure`）の予定が枠を持ったまま座標を持たない点も現状維持。

### 理由

オフライン時に一切サポートできなくなるより、枠を1つ消費するほうが損失が小さい。
一時失敗は通信が戻れば翌日には解消する類のもので、恒久失敗と違って
24時間キャッシュもしていないため、次回起動で必ず再試行される。

### 出発時刻の計算との関係

`noLocationKeys ∩ todaySlots.confirmedKeys` が「枠は持っているが出発時刻を計算できない
予定」になる。spec.md 2-3 の「前のサポート対象に場所がない場合 → 自宅から」は
この集合の判定にあたる。

## 決定10: 取得範囲外のスナップショットと保存期間の境界

### 決定

現在の実装のまま確定とする。

- 取得範囲（3日前〜30日後）の外にあるスナップショットは削除判定から外す。
- `RetentionPolicy` の境界は、スナップショットが完了から14日以上で削除（13日は残る）、
  枠は「3日前の0時より前」を削除（3日前ちょうどは残る）、失敗キャッシュは24時間以上で削除。

### 理由

前者は、完了済みスナップショットが14日残る一方で取得は3日前からなので、そのまま
削除判定に渡すと「取得結果に無い＝外部で削除された」と誤判定するため。
後者は仕様の意図が明確で、影響範囲も保存期間の中に閉じている。
どちらも出発時刻の計算には影響しない。

## 未確定の論点

以下は実装で暫定的に決めた既定値。運用データが出てから判断する。

### ジオコーディングのキャッシュキーの正規化

キーは `locationText` の前後の空白を除いた文字列。大文字小文字や全角半角の正規化は
していない。同じ場所を二重にジオコーディングしうるため、レート制限と
1日3件ぶんの呼び出し枠を無駄に消費する可能性がある。出発時刻の値そのものは変わらない。

### AppleGeocodingService のエラー分類

`CLError.network` に加え、`MKError` の `.loadingThrottled` / `.serverFailure` も
一時失敗として扱っている。一時失敗と判定されると、その予定は枠を持ったまま座標を
持たない状態になる（決定9）。恒久失敗なら枠を消費しない。分類のずれは
「出発時刻を計算できない予定が枠を占有する頻度」を左右する。

実機で CLGeocoder / MKLocalSearch がどのエラーを返すかを見てから調整する。
